# وَصْل WASL — تصميم المنصة الفعلية (الإصدار الأول)

تاريخ: 2026-11-23

## 1. الهدف ولماذا

وَصْل منظومة لإدارة انصراف الطلاب من المدارس. المشتري هو المدرسة، والمستخدمون اليوميون هم ولي الأمر وموظفة الانصراف. الهدف: ولي الأمر يُعلن أنه في الطريق، فتجهّز المدرسة الطالب قبل وصوله، ويتم التسليم فقط للمستلم المخوّل بعد التحقق، ويُحفظ سجل كل عملية.

المطلوب **نظام فعلي**: حسابات حقيقية، قاعدة بيانات، تحديث لحظي، وإشعارات تصل فعلاً لجوال ولي الأمر. يجب أن يخدم أكثر من مدرسة وفرع منذ البداية.

الهوية: مؤسسية وموثوقة، ليست طفولية. الألوان: أزرق عميق `#123B67`، تركوازي `#168C91`، رمادي فاتح `#F2F5F8`، أبيض. الشعار اللفظي: «انصراف منظم.. واطمئنان يدوم». الواجهة عربية RTL. الصفحة التعريفية والعرض التفاعلي الحاليان (https://claude.ai/artifact/7hWsHFfL5z9ztTTD5ahEQ1) مرجع بصري لشكل الواجهات.

## 2. الأهداف

نطاق الإطلاق الأول (14 بنداً، من صاحب المشروع):

1. تسجيل حسابات المدارس والفروع
2. تسجيل أولياء الأمور واعتمادهم
3. إدارة الطلاب والفصول والجداول
4. تذكير ولي الأمر قبل الانصراف بـ15 دقيقة
5. إشعار انتهاء الدوام
6. إنشاء طلبات الاستلام وإدارتها
7. تحديث موقع ولي الأمر خلال الرحلة النشطة
8. حالات الطالب وموقعه التشغيلي
9. لوحة المدرسة والتحديث الفوري
10. واجهة موظفة الانصراف
11. التحقق عبر QR أو رمز استلام
12. تأكيد التسليم وسجل العمليات
13. إدارة الصلاحيات والتقارير الأساسية
14. سياسة الخصوصية والحماية والنسخ الاحتياطي

## 3. ما ليس ضمن الإصدار الأول (Non-goals)

- تطبيق جوال أصلي (Flutter / React Native). القرار: **منصة إلكترونية** تعمل من المتصفح وتُثبَّت على الشاشة الرئيسية (PWA). التطبيق الأصلي لاحقاً على نفس الخادم.
- مزود خرائط مدفوع ومسارات القيادة. وقت الوصول المتوقع تقديري (انظر 7.4).
- الدفع والاشتراكات والفوترة للمدارس.
- واجهة إنجليزية.
- التكامل مع أنظمة المدارس الخارجية (نور وغيرها). الإدخال برفع ملف أو يدوياً.

## 4. ما يُعد فشلاً حتى لو عمل النظام (Anti-goals)

- تتبع موقع الطفل جغرافياً بأي شكل. «موقع الطالب» حالة تشغيلية فقط داخل المدرسة.
- الاعتماد على GPS وحده لإثبات وصول ولي الأمر أو للسماح بالتسليم. التسليم يتم فقط بعد تحقق الموظفة.
- تسليم طالب لشخص غير مخوّل، أو إظهار أسماء الطلاب في الشاشة المركزية العامة.
- مشاركة موقع ولي الأمر خارج الرحلة النشطة، أو الاحتفاظ بمسار رحلته بعد إغلاق الطلب.
- مدرسة ترى بيانات مدرسة أخرى.

## 5. القيود

- البيانات شخصية ومتعلقة بقاصرين: الالتزام بمبادئ نظام حماية البيانات الشخصية في السعودية (PDPL): تقليل البيانات، الغرض المحدد، سجل تدقيق، حذف موقع ولي الأمر بعد الرحلة.
- المنطقة الزمنية `Asia/Riyadh`. أسبوع الدراسة الافتراضي الأحد–الخميس (قابل للتعديل لكل مدرسة).
- الإشعارات عبر Web Push: على iPhone تعمل فقط بعد إضافة المنصة للشاشة الرئيسية (iOS 16.4+). يجب أن تشرح الواجهة ذلك لولي الأمر.
- مشاركة الموقع من المتصفح تتوقف غالباً عندما تكون الصفحة في الخلفية أو الشاشة مقفلة. النظام يعرض «آخر تحديث» ولا يفترض الدقة.
- هذه الجلسة مؤقتة: الكود يُحفظ في مستودع GitHub الخاص بصاحب المشروع.

## 6. الطرق التي دُرست (Approaches)

| الطريقة | المزايا | العيوب |
|---|---|---|
| **أ) تطبيق Next.js واحد متكامل** (الواجهات + الخادم + WebSockets) مع PostgreSQL | أسرع بناء، نشر واحد، تكلفة أقل، الخادم يخدم تطبيق جوال لاحقاً | فصل أقل بين الواجهة والخادم |
| ب) خادم Node.js منفصل + واجهة Next.js منفصلة | فصل أوضح لفريق أكبر | عمل أكثر بحوالي الثلث، نظامان للنشر والصيانة |
| ج) خدمة جاهزة (Supabase) | الأسرع في البداية | البيانات عند طرف خارجي يصعب التحكم بمكان تخزينه، غير مناسب لبيانات الطلاب |

**المختار: (أ)** — اختاره صاحب المشروع.

## 7. التصميم

### 7.1 الأدوار

| الدور | من ينشئه | ماذا يرى ويفعل |
|---|---|---|
| مشرف المنصة | يُنشأ عند الإعداد | ينشئ المدارس ويعيّن مدير كل مدرسة |
| مدير المدرسة | مشرف المنصة | يدير الفروع، البوابات، الفصول، الجداول، الطلاب، أولياء الأمور، الموظفات، الاعتمادات، التقارير. صلاحيته على مدرسته فقط (كل فروعها) |
| موظفة الانصراف | مدير المدرسة | واجهة الموظفة لفرع واحد (وبوابات محددة اختيارياً) |
| ولي الأمر | يسجّل بنفسه بعد أن ترفع المدرسة بياناته | يرى أبناءه المرتبطين برقمه، يطلب الاستلام، يضيف مستلمين مفوّضين |
| المستلم المفوّض | يضيفه ولي الأمر وتعتمده المدرسة | حساب خاص به، يرى فقط الأبناء المفوّض عليهم، ويطلب استلامهم |
| الشاشة المركزية | رابط سري لكل فرع ينشئه مدير المدرسة | أرقام الطلبات والحالات فقط، بدون تسجيل دخول وبدون أسماء |

### 7.2 الحسابات وتسجيل الدخول

قرار صاحب المشروع: **الدخول باسم مستخدم وكلمة مرور**، والتحقق برسالة.

- **أولياء الأمور والمفوّضون:** اسم المستخدم هو رقم الجوال أو البريد الإلكتروني.
  - التسجيل أول مرة: يدخل رقم جواله (أو بريده) ← يصله رمز تحقق برسالة SMS (أو بريد) ← يعيّن كلمة مرور ← يدخل.
  - الدخول بعدها: رقم الجوال/البريد + كلمة المرور.
  - نسيت كلمة المرور: رمز تحقق برسالة ثم كلمة مرور جديدة.
  - لا يُطلب رقم الهوية (قرار صاحب المشروع: نكتفي برقم الجوال).
- **مدير المدرسة والموظفات:** اسم مستخدم وكلمة مرور ينشئها من هو أعلى منه، مع إلزام تغييرها عند أول دخول.
- رسائل SMS عبر محوّل (adapter) لمزود سعودي (Unifonic أو Taqnyat). قبل تفعيل المزود يعمل «وضع التطوير»: الرمز يُسجَّل في سجل الخادم ويظهر لمشرف المنصة، ولا يُرسل.
- البريد عبر SMTP أو خدمة بريد (Resend) خلف محوّل.
- الأمان: كلمات المرور مشفرة (argon2 أو bcrypt)، جلسات بكوكي httpOnly، حد لمحاولات الدخول وطلب الرموز، صلاحية رمز التحقق 5 دقائق.

### 7.3 الربط والاعتماد

- المدرسة ترفع ملف Excel/CSV للطلاب: الاسم، الفرع، الفصل، البوابة الافتراضية، ورقم جوال أو أكثر لأولياء الأمور (الأب والأم معاً مثلاً). أو تضيفهم يدوياً.
- عند تسجيل ولي الأمر برقمه، تظهر له كل السجلات التي تحمل رقمه في أي مدرسة أو فرع، في حساب واحد. **الربط القادم من بيانات المدرسة معتمد تلقائياً** لأن المدرسة مصدره.
- إن كان التسجيل بالبريد، يربط ولي الأمر رقم جواله لاحقاً (بتحقق برسالة) حتى يظهر أبناؤه.
- **المستلم المفوّض (طلب صاحب المشروع):** ولي الأمر يضيف «شخصاً آخر يستلم الأبناء» بالاسم ورقم الجوال، ويختار الأبناء المشمولين. يدخل الطلب قائمة «بانتظار الاعتماد» في لوحة المدرسة. بعد الاعتماد يسجّل المفوّض برقمه مثل ولي الأمر ويرى فقط أولئك الأبناء. ولي الأمر يستطيع إلغاء التفويض في أي وقت.
- المدرسة تستطيع إيقاف أي ربط أو تفويض.

### 7.4 دورة طلب الاستلام

حالات الطالب لكل يوم: `داخل المدرسة` ← `في الطريق` (يوجد طلب) ← `قيد التجهيز` ← `جاهز للاستلام` ← `تم التسليم`. وحالة `ملغى` للطلب.

1. ولي الأمر يضغط «أنا في الطريق» ويختار ابناً أو أكثر من نفس الفرع (طلب واحد لعدة أبناء). يُطلب إذن الموقع؛ رفض الإذن لا يمنع الطلب.
2. يُنشأ طلب برقم قصير (تسلسلي لكل فرع لكل يوم) ورمز استلام من 6 أرقام ورمز QR يحمل معرّفاً موقّعاً للطلب.
3. أثناء الرحلة: المتصفح يرسل الموقع كل 15–30 ثانية. الخادم يحفظ **آخر نقطة فقط** ويحسب وقت الوصول التقديري = المسافة المستقيمة ÷ سرعة افتراضية (30 كم/س، قابلة للتعديل). يظهر في اللوحة مع «آخر تحديث قبل X».
4. ولي الأمر يستطيع الضغط على «وصلت». هذا معلومة للمدرسة فقط وليس شرطاً للتسليم.
5. الموظفة: «بدء التجهيز» ← «جاهز للاستلام» (لكل طالب في الطلب).
6. التحقق: الموظفة تمسح QR بكاميرا الجهاز من المتصفح أو تدخل رمز الاستلام. النظام يظهر اسم المستلم وصفته (ولي أمر / مفوّض) وصورته إن وُجدت والطلاب المعنيين.
   - رمز الاستلام وQR يظهران فقط داخل حساب المستلم وهو مسجّل الدخول، ويتجددان كل دقيقة (رمز مبني على الوقت ومرتبط بالطلب)، حتى لا تنفع صورة الشاشة.
   - صورة المستلم: **إلزامية للمفوّض**، اختيارية لولي الأمر. تُحفظ مشفرة، لا تظهر إلا للموظفة لحظة التحقق ولمدير المدرسة عند الاعتماد، وتُحذف عند إلغاء التفويض.
7. «تأكيد التسليم» يغلق الطلب: يتوقف إرسال الموقع، تُحذف نقطة الموقع، ويُحفظ السجل (من طلب، من سلّم، أوقات كل حالة، طريقة التحقق).
8. **قواعد الطلب (قرار المنفّذ):** يمكن إنشاء الطلب في يوم دراسي فقط، من 60 دقيقة قبل موعد انصراف الابن حتى نهاية الدوام (المدة قابلة للتعديل لكل مدرسة). لا طلبات في الإجازات. الاستئذان المبكر وسط اليوم خارج الإصدار الأول.
9. **الطالب لا يكون إلا في طلب نشط واحد:** إذا حاول ولي أمر أو مفوّض آخر طلبه، تظهر رسالة «يوجد طلب نشط لهذا الابن من (الاسم)». البوابة هي البوابة الافتراضية للطالب، والموظفة تستطيع تغييرها، وإن اختلفت بوابات الإخوة في طلب واحد تُستخدم بوابة أصغرهم ويمكن للموظفة التعديل.
10. إلغاء الطلب ممكن من ولي الأمر قبل التسليم، ومن المدرسة مع ذكر السبب.

### 7.5 الإشعارات

- Web Push بمفاتيح VAPID (بدون Firebase). ولي الأمر يفعّلها من المنصة، ولكل جهاز اشتراك.
- مجدول مهام داخل الخادم (pg-boss على PostgreSQL) يرسل:
  - تذكير قبل موعد انصراف كل ابن بـ15 دقيقة (حسب جدول فصله ذلك اليوم).
  - إشعار انتهاء الدوام عند الموعد.
  - تغيّر الحالة: «قيد التجهيز»، «جاهز للاستلام»، «تم التسليم».
- التذكير وإشعار انتهاء الدوام يصلان لكل أولياء الأمور المرتبطين بالطالب. المفوّض يستلمها فقط إن فعّلها بنفسه (قرار المنفّذ).
- كل إشعار يظهر أيضاً داخل المنصة (لمن لم يفعّل الإشعارات).
- لا يرسل التذكير لأيام الإجازة المعرّفة في تقويم المدرسة.

### 7.6 الجداول

- لكل فصل موعد انصراف لكل يوم من أيام الأسبوع.
- المدرسة تعرّف أيام الإجازات، واستثناء ليوم محدد (انصراف مبكر) على مستوى الفرع أو الفصل.

### 7.7 التحديث اللحظي

- Socket.IO على خادم Node مخصص يشغّل Next.js.
- غرف: لكل فرع (اللوحة، الموظفات، الشاشة المركزية) ولكل ولي أمر. الشاشة المركزية تستلم فقط رقم الطلب والحالة والبوابة.
- السعة المستهدفة للإصدار الأول (قرار المنفّذ): حتى 10 مدارس وحتى 1500 طالب للفرع، بنسخة خادم واحدة. التصميم يسمح بإضافة Redis adapter وعدة نسخ لاحقاً دون تغيير الواجهات.
- عند فقدان الاتصال تعيد الواجهة جلب الحالة كاملة.

### 7.8 الواجهات

- **ولي الأمر (جوال أولاً):** الرئيسية: الأبناء، المدرسة، موعد الانصراف، الحالة، زر «أنا في الطريق». شاشة الطلب النشط: الحالة، مؤشر مشاركة الموقع، رمز الاستلام وQR. السجل. المفوّضون. الإعدادات (الإشعارات، كلمة المرور).
- **الموظفة (جهاز لوحي/جوال):** قائمة الطلبات النشطة مرتبة (جاهز، قيد التجهيز، في الطريق حسب الوصول)، بحث بالاسم أو رقم الطلب، مسح QR، أزرار الحالة، التحقق والتسليم.
- **مدير المدرسة (حاسب):** لوحة لحظية (مؤشرات + جدول الطلبات + سجل الأحداث)، إدارة الفروع والبوابات والفصول والجداول والطلاب (مع رفع الملف) وأولياء الأمور والموظفات، قائمة الاعتمادات، التقارير، روابط الشاشات المركزية.
- **مشرف المنصة:** إنشاء المدارس ومديريها، رؤية رموز التحقق في وضع التطوير.
- **الشاشة المركزية (شاشة كبيرة):** عمودان «قيد التجهيز» و«جاهز للاستلام» بأرقام الطلبات والبوابة.

### 7.9 التقارير الأساسية

لكل فرع ولفترة زمنية: عدد الطلبات، متوسط وأقصى وقت الانتظار (من «جاهز» إلى «تم التسليم»، ومن إنشاء الطلب إلى التسليم)، الازدحام لكل 15 دقيقة ولكل بوابة، الطلبات الملغاة. عرض في الصفحة مع تصدير CSV.

### 7.10 الخصوصية والحماية والنسخ الاحتياطي

- عزل البيانات بين المدارس في كل استعلام (كل جدول يحمل معرّف المدرسة، وفحص الصلاحية في طبقة واحدة مركزية).
- سجل تدقيق لكل عملية حساسة: تسجيل الدخول، الاعتمادات، تغييرات البيانات، التسليم.
- موقع ولي الأمر: آخر نقطة فقط، تُحذف عند إغلاق الطلب أو إلغائه أو نهاية اليوم.
- سجلات الطلبات تُحفظ سنة دراسية واحدة افتراضياً (قابلة للتعديل).
- صفحة سياسة الخصوصية وشروط الاستخدام بالعربية، وموافقة ولي الأمر عند التسجيل وعند أول مشاركة موقع.
- HTTPS فقط، ترويسات أمان، حد للطلبات.
- نسخ احتياطي يومي لقاعدة البيانات من مزود الاستضافة، مع تعليمات استعادة موثقة.

### 7.11 التقنية والاستضافة

- Next.js (App Router) + TypeScript، خادم Node مخصص مع Socket.IO.
- PostgreSQL مع Prisma.
- pg-boss للمهام المجدولة، web-push للإشعارات.
- Tailwind CSS بألوان الهوية، خط IBM Plex Sans Arabic وReadex Pro.
- مسح QR في المتصفح بمكتبة مثل `html5-qrcode`.
- Dockerfile ليكون النشر قابلاً للنقل. الاستضافة الافتراضية: Railway (التطبيق + PostgreSQL مع النسخ الاحتياطي)، مع إمكانية النقل لاحقاً لسحابة داخل السعودية.
- الاختبارات: Vitest لمنطق الحالات والصلاحيات، Playwright لرحلة الاستلام الكاملة.

### 7.12 بيانات أساسية (مسودة الجداول)

`School`, `Branch`, `Gate`, `Classroom`, `ClassSchedule` (يوم الأسبوع، الموعد), `Holiday`/`ScheduleOverride`, `Student` (الفرع، الفصل، البوابة), `GuardianPhone` (طالب ↔ رقم جوال، من المدرسة), `User` (الدور، الجوال/البريد/اسم المستخدم، كلمة المرور المشفرة), `Delegation` (ولي الأمر، المفوّض، الأبناء، الحالة), `PickupRequest` (الفرع، الرقم اليومي، من طلب، رمز الاستلام، الحالة، آخر موقع، وقت الوصول التقديري), `PickupItem` (طالب ↔ طلب، حالة وأوقات كل مرحلة), `PushSubscription`, `Notification`, `AuditLog`, `OtpCode`, `BoardToken`.

## 8. ما يُترك للمنفّذ

- هيكلة المجلدات، أسماء الملفات، تفاصيل مخطط قاعدة البيانات.
- اختيار المكتبات الفرعية داخل الإطار المذكور.
- تفاصيل التصميم البصري ضمن الهوية والمرجع البصري.
- ترتيب البناء، بشرط أن تعمل رحلة الاستلام الكاملة مبكراً.

## 9. ما يحتاجه صاحب المشروع لاحقاً (ليس شرطاً لبدء البناء)

- مستودع GitHub (الاسم مطلوب الآن).
- حساب استضافة (Railway أو غيره) عند النشر.
- حساب مزود SMS واسم مرسل معتمد، وحساب بريد للإرسال.
- نطاق (دومين) للمنصة.
